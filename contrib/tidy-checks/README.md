# cvc5 clang-tidy checks

This directory builds `Cvc5TidyChecks.so`, a clang-tidy plugin module
(`cvc5-module`) that registers cvc5-specific checks. The checks are enabled by
the `cvc5-*` entry in the top-level [`.clang-tidy`](../../.clang-tidy).
The `static-analysis` build of the cvc5 buildbot runs them nightly.

Currently one check is provided: `cvc5-node-id-determinism`.

## `cvc5-node-id-determinism`

### Why it exists

cvc5 assigns every `Node` a unique id drawn from a global counter,
`NodeManager::d_nextId`. Only two functions create a new id from it:
`NodeManager::mkConstInternal` and `NodeBuilder::constructNV`. Both look the
node up in the node manager's pool first and return the existing node when they
find one, so a call creates a new id only when the node is genuinely new.

C++ leaves the evaluation order of function arguments and of most binary
operands *unspecified*. So in

```cpp
Node n = nm->mkNode(Kind::AND, f(), g());
```

a compiler may call `f()` before `g()` or the other way around. If both
transitively create node ids, the two nodes end up with ids swapped depending
on the compiler, its version, or the optimization level. Node ids feed into
term ordering and hashing, so this leaks out as different solver behaviour —
different answers on `sat`/`unsat` traces, different models, unreproducible
runs — from source that looks deterministic.

The check finds these expressions and, where it can, rewrites them.

### What it flags

An expression is reported when **two or more** calls that create node ids
appear in a context the compiler is free to reorder. A single such call cannot
race with itself, so it is never reported.

Following the C++17 sequencing rules (P0145R3):

| Context | Treated as | Behaviour |
| --- | --- | --- |
| Function/method arguments `f(a, b)` | unsequenced | flagged |
| Constructor arguments `T(a, b)` | unsequenced | flagged |
| Most binary operators `a + b`, `a * b`, `a == b` | unsequenced | flagged |
| Assignment `a = b`, compound assignment `a += b` | sequenced (RHS before LHS) | each side checked independently |
| `a << b`, `a >> b` (built-in and overloaded) | sequenced left-to-right | not flagged |
| `a && b`, `a \|\| b`, `a , b` | sequenced | not flagged |
| Braced init `T{a, b}`, `f({a, b})` | sequenced left-to-right | not flagged |

### How to fix a warning

**For `mkNode` with more than one child argument**, the check emits a fix-it:
wrap the children in braces. A braced-init-list is sequenced left-to-right, so
the ids are created in source order.

```cpp
// flagged
Node n = nm->mkNode(Kind::AND, f(), g());
// fixed (this is what the fix-it produces)
Node n = nm->mkNode(Kind::AND, {f(), g()});
```

Apply it with `run-clang-tidy -fix ...`, or by hand.

**Everywhere else**, hoist the calls into named locals so that the order is
written down explicitly:

```cpp
// flagged: both getSort() calls can create ids, in unspecified order
assert(t.getSort() == tt.getSort());
// fixed
Sort t_sort = t.getSort();
Sort tt_sort = tt.getSort();
assert(t_sort == tt_sort);
```

(That example is from
[`test/api/cpp/issues/proj-issue337.cpp`](../../test/api/cpp/issues/proj-issue337.cpp).)

Note that declarations are separate full-expressions, so splitting into two
statements is always sufficient. Do **not** silence a report by reordering the
arguments — that changes which id is assigned first without making the order
defined.

### The dependency list

The check does not know by itself which functions create node ids; it reads a
list of fully qualified names from a CSV file given by the
`NodeIdDependencyListPath` check option. Without that option the check loads no
names and reports nothing (it prints a warning to stderr).

The list is generated by
[`contrib/codeql/IdentifyNodeIdDependentCalls.ql`](../codeql/IdentifyNodeIdDependentCalls.ql),
a CodeQL query that computes the transitive closure of callers of the two
functions that create node ids, which it names `NodeIdMintingPoint`,
restricted to the analyzed source tree. `operator<<` and `operator>>` entries
are dropped when the list is loaded, since those are sequenced anyway.

Because the list comes from a whole-program CodeQL database, running the check
locally requires building cvc5 under `codeql database create` first.

## Running the checks locally

The plugin must be built against the **same LLVM/Clang version** as the
`clang-tidy` binary that loads it. The nightly uses 22; the commands below
follow it step for step, so adjust `LLVM_VERSION` if your toolchain differs.

```bash
export LLVM_VERSION=22

# 1. Build the plugin
mkdir -p deps/cvc5-tidy-checks && cd deps/cvc5-tidy-checks
cmake ../../contrib/tidy-checks/ \
      -DLLVM_DIR=/usr/lib/llvm-$LLVM_VERSION/lib/cmake/llvm \
      -DClang_DIR=/usr/lib/llvm-$LLVM_VERSION/lib/cmake/clang
make -j$(nproc)
cd ../..

# 2. Build cvc5 into a CodeQL database
export CC=clang-$LLVM_VERSION CXX=clang++-$LLVM_VERSION
./configure.sh --auto-download unrestricted --assertions
cd build/
# --overwrite: a database left over from a previous run would get in the way
codeql database create codeql-db --overwrite --language=cpp \
       --command="make -j$(nproc)"

# 3. Generate the NodeId dependency list
codeql pack install ../contrib/codeql
codeql query run ../contrib/codeql/IdentifyNodeIdDependentCalls.ql \
       --database=codeql-db --output=node_id_dependencies.bqrs
codeql bqrs decode node_id_dependencies.bqrs \
       --format=csv --output=node_id_dependencies.csv
cd ..

# 4. Run clang-tidy with the plugin
export NODE_DEP_PATH=$(pwd)/build/node_id_dependencies.csv
CFG='{InheritParentConfig: true, CheckOptions: [{key: cvc5-node-id-determinism.NodeIdDependencyListPath, value: "'"$NODE_DEP_PATH"'"}]}'
run-clang-tidy-$LLVM_VERSION -clang-tidy-binary clang-tidy-$LLVM_VERSION \
               -quiet -warnings-as-errors "*" \
               -config="$CFG" \
               -load deps/cvc5-tidy-checks/Cvc5TidyChecks.so \
               -p build -j$(nproc)
```

`-clang-tidy-binary` is only needed where no unversioned `clang-tidy` is on
`PATH`, as is the case in the nightly image.

Add `-fix` to step 4 to apply the `mkNode` fix-its. To check a single file,
pass it as a positional regex argument to `run-clang-tidy`.

The nightly runs step 4 with `-warnings-as-errors "*"`, so any report fails the
build.

## Adding a new check

1. Add `MyCheck.{h,cpp}` deriving from `ClangTidyCheck`.
2. Add the `.cpp` to the `add_library` call in
   [`CMakeLists.txt`](CMakeLists.txt).
3. Register it in
   [`Cvc5TidyModule.cpp`](Cvc5TidyModule.cpp) with a `cvc5-`-prefixed name; the
   `cvc5-*` glob in the top-level `.clang-tidy` then picks it up automatically.

Note that `Cvc5TidyModule.cpp` includes `clang-tidy/ClangTidyModuleRegistry.h`,
which is deprecated: it is removed in LLVM 24, and its symbols move to
`ClangTidyModule.h`. The include has to be updated before the checks can be
built against LLVM 24 or newer.
